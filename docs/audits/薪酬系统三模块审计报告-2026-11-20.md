## 二、严重问题

### S1. 采购填报列表：项目账号匹配不到项目时能看到全部项目明细（越权）

- 位置：`app/Purchase/handlers/fill.php::handle_fill_items()` 第 20–37 行；项目映射在 `app/Http/Controllers/Api/PurchaseController.php` 第 30–46 行。
- 触发条件：项目账号的 `project_name` 在主库 `payroll_projects` 中查不到（项目改名、停用、组织架构未同步、账号未挂项目）→ 控制器 `projectId=null` → 上下文 `project_id=0` → 查询条件 `if ($project_id > 0)` 不成立，**项目过滤被整体跳过**。
- 实测：上下文 `project_id=0` 时 `handle_fill_items('2026-10')` 返回 **4 条、项目 1 和 2 都有**；`project_id=2` 时只返回本项目 1 条。
- 影响：任意项目账号可读取所有项目的采购品名、规格、数量、库存、申购原因、使用位置、备注；属于跨项目数据泄露，且不需要构造特殊参数，账号异常即可触发。
- 复现：`project_id=0` + `GET /api/purchase/fill/items?month=2026-10`。
- 建议修法：`role !== 'admin'` 时，`project_id <= 0` 直接返回 403/空集；控制器侧对“项目账号但无法映射项目”的账号拒绝进入采购模块并记审计日志。
- 预估工作量：0.2 人日（含回归：项目名不存在时返回 403、正常项目只返回本项目）。

### S2. 报价导入按整月清空重灌，部分文件会删除其他项目的存档（数据丢失）

- 位置：`app/Purchase/handlers/export_import.php::handle_import_archive()` 第 409–451 行。
- 机制：同一个事务里先 `DELETE FROM archived_purchases WHERE month=?`，再只插入上传 Excel 中出现的行；`archived_purchases` 没有与 `purchase_items.id` 的关联键，无法判断“本次文件覆盖了哪些行”。
- 触发条件：上传的 Excel 被裁剪（只保留部分项目/条线）、分批导入、或导出的汇总表被手工删行后回传。
- 影响：该月其他项目已导入的报价与金额被静默删除 → 预算执行率、汇总、驾驶舱、年度明细同时变小；无变更前快照、日志只记“新增 N 条”，无法还原。
- 复现（代码路径）：导入项目甲后，再导入只含项目乙的文件 → 项目甲当月存档为 0。CLI 无法模拟 `is_uploaded_file()`，本轮以代码核对确认。
- 建议修法：改为按（月份 + 项目 + 条线 + 行）增量 upsert；或导入前把该月存档写入快照表，删除范围限定为“文件中出现的项目/条线”，并在日志中记录删除条数与金额。
- 预估工作量：0.5–1 人日。

### S3. 报表中心与薪酬/考勤源头口径不一致（同月数字对不上）

- 位置：`app/Http/Controllers/Api/ReportController.php`
  - 驾驶舱 `dashboard()` 第 17–58 行、人力 `hrReport()/hrKpis()` 第 76–170 行、薪酬 `salaryReport()` 第 259–383 行，均通过 `scopedResults()` 只按 `year_month + project_name` 取数，**不区分基层/管理/案场行**。
  - 薪酬汇总（上一批已修复）已按“项目合计 = 基层 + 管理，案场单列”输出，两者口径分叉。
- 实测：甲项目 2026-10 造 员工 1000 + 管理人员 5000 + 案场 800：
  - 项目账号 `/api/dashboard?ym=2026-10` → `month_gross=6800`、`month_headcount=3`、项目行 `gross=6800`，无任何分类拆分字段；
  - `/api/report/hr` 的 `cost_by_project.gross=6000`（员工+管理），`kpis.avg_pay=3000`（把管理人员计入人均）；
  - 薪酬汇总页同月会显示“基层 1000 / 管理 5000 / 案场 800 单列”。
- 影响：同一月份在驾驶舱、人力报表、薪酬汇总、工资表看到不同数字；项目账号无法判断 6800 里哪部分是管理人员成本（该可见性本身是上一批确认保留的，不算新增越权，但**没有分列就无法对账**）。
- 建议修法：报表接口统一复用薪酬汇总的行类型口径，返回 `staff_gross / manager_gross / case_gross` 三块与合计；人均应发按“基层+管理”或明确标注包含范围；前端标注每块含义。
- 预估工作量：1 人日（后端 0.5 + 前端 0.3 + 回归 0.2）。

## 三、一般问题

### M1. 采购状态机可跳过“提交”直接确认；撤销确认可把“已退回”直接变回“已提交”

- 位置：`app/Purchase/handlers/admin.php::handle_admin_confirm_item()` 第 90–106 行、`handle_admin_unconfirm_item()` 第 157–165 行。
- 实测：`draft` 记录调用确认 → `status=confirmed`；`returned` 记录调用撤销确认 → `status=submitted`。
- 影响：审计上出现“未提交即确认”“已退回未经修改直接回到提交”，与“退回后须员工重新提交”的规则冲突；可被用来绕过退回原因整改。
- 建议：确认只允许 `submitted`；撤销确认只允许 `confirmed` 且回到 `submitted`，`returned` 状态不可被撤销确认覆盖；集中到一个 `transition()` 函数。
- 预估：0.3 人日。

### M2. 归档不校验报价是否已导入，归档后导入被永久拒绝

- 位置：`admin.php::handle_admin_archive()` 第 204–228 行；导入前置检查在 `export_import.php` 第 373 行。
- 实测：4 条全部确认、`archived_purchases=0` 时归档成功，返回“已归档锁定”；此后导入被 `month_archived()` 拒绝，只能先“撤销归档”。
- 影响：误归档后该月没有单价/金额，汇总与预算执行率全为 0；恢复需要管理员知道“先撤销归档”，无提示。
- 建议：归档前校验该月存档非空（或弹出二次确认写明“未导入报价将导致金额为 0”）；归档提示中给出恢复方式。
- 预估：0.3 人日。

### M3. 删除“已退回”明细会连带删除同月同项目同名称同规格的存档采购行

- 位置：`fill.php::handle_fill_delete()` 第 215–218 行。
- 实测：先存在 1 条存档，删除同月同项目同名称同规格的退回记录后，存档行数 1 → 0。
- 影响：存档是报表/预算的唯一金额来源，误删会导致金额丢失；不同条线同名称同规格也会被误伤（SQL 未带 line）。
- 建议：存档增加 `item_id` 关联，按 id 删除；短期至少把 `line`、`brand`、`unit` 加入条件，且仅在存档确由该填报生成时删除。
- 预估：0.5 人日。

### M4. 采购数量/库存没有非负、上限和数值校验（前后端都没有）

- 位置：`fill.php::handle_fill_create()` 第 63–73 行、`handle_fill_update()` 第 108–134 行（`(float)` 强转）。
- 实测：新增 `quantity=-5, stock=-2` 保存成功并原样落库；项目账号对“已退回”记录改成负数量也成功，并把状态改成 `draft`。
- 影响：负数量会生成负金额，冲减汇总与预算；库存字段无台账，负数无人拦截；`(float)"abc"` 静默变 0。
- 建议：后端数量必须 > 0、库存 >= 0、限制两位小数与合理上限；前端同步校验；导入报价同样校验数量和单价。
- 预估：0.3 人日。

### M5. 报表中心没有“项目/分类”筛选，只有月份/年份

- 位置：`frontend/src/modules/report/SalaryReport.vue` 第 158 行、`AttReport.vue` 第 111 行、`HrReport.vue` 第 142 行；后端 `ReportController` 只读取 `ym/year/annual`。
- 影响：用户要求的“月份、项目、分类”筛选中，项目与分类无法使用；项目账号只能看本项目（这部分正确）。
- 建议：后端增加 `project`、`category`（基层/管理/案场）参数并落到 SQL；前端加筛选控件；或明确产品上不提供并移除相关预期。
- 预估：0.5–1 人日。

### M6. 考勤报表不读取上传的应出勤/实际出勤统计列，按符号重新计算

- 位置：`ReportController::attendanceReport()` 第 396–501 行（只读 `rows.days` 符号）。
- 实测：考勤行存 `req_attend=22、act_attend=22`，但 `days` 只有 `["√","事"]` → 报表输出应出勤 2、实际 1、出勤率 50%，与考勤表/核算口径（22/22）不一致。
- 影响：正常上传时符号与统计列一致则无感；但上传允许“应出勤手填”与符号不同，此时报表与工资口径分裂，且页面不提示。
- 建议：存在 `req_attend/act_attend` 时优先采用，缺失再回退符号统计；或在报表标注“按符号统计”。
- 预估：0.5 人日。

### M7. 报表逐月重复查询、全年数据在 PHP 侧聚合（无分页）

- 位置：`ReportController::dashboard()` 第 45–50 行、`salaryReport()` 第 322–337/360–366 行、`attendanceReport()` 第 460–475 行。
- 实测：单个 `/api/report/salary?ym=2026-12` 请求触发 **超过 20 次查询**（12 月趋势 12 次 + 预算趋势再 12 次 + 当月/上月/累计/预算/在职人数）；累计数据 `year_month like '2026-%'` 全量取回后在 PHP 过滤。
- 影响：账套越大越慢，容易超时；与上次审计 M7 同类，报表中心尚未治理。
- 建议：一次 `GROUP BY year_month` 聚合；`payroll_results(year_month)` 已有索引，按范围查询；预算一次取回后在内存拼 12 个月。
- 预估：0.5 人日。

### M8. 人员档案导出未过滤已删除人员（与人员列表口径不一致）

- 位置：`ReportController::staffExport()` 第 503–517 行（无 `deleted=false`）。
- 实测：`deleted=true` 的员工仍出现在导出 Excel 中；项目账号的 `project` 参数被忽略（项目范围仍然生效，这部分正确）。
- 影响：导出人数大于页面人数；若业务要“全部历史人员”则属于口径缺说明，否则是错数据。
- 建议：默认过滤 `deleted=false`，需要历史人员时增加显式参数和“已删除”列。
- 预估：0.1 人日。

### M9. 维保：合同已不存在时，孤立附件/履约记录跳过归属校验，任意项目账号可改可删

- 位置：`MaintenanceController::updateRecord()` 第 235–236 行、`deleteRecord()` 第 256–257 行、`deleteAttachment()` 第 180–181 行（均为 `if ($contract && ...)`）。
- 实测：合同 id 999 不存在时，项目账号修改记录、删除记录、删除附件均返回 200。
- 影响：历史残留/手工造数可被跨项目账号操作；不涉及正常合同数据（正常路径校验完整）。
- 建议：合同不存在直接 404，不进入写操作；定期清理孤儿行。
- 预估：0.2 人日。

### M10. 采购报价导入与填报状态无关联，草稿未确认也能先导入报价

- 位置：`export_import.php::handle_import_archive()` 全程无 `purchase_items.status` 校验。
- 实测：存在草稿时导入成功，存档直接生成。
- 影响：报价先于确认落库，之后员工修改数量/规格不会回写存档 → 存档与最终填报不一致；归档时只看“全部确认”，不看存档是否匹配。
- 建议：导入前要求该月填报全部 `confirmed`，或导入后按 `purchase_items` 重新生成存档并比对差异提示。
- 预估：0.5 人日。

### M11. 管理员导出在“未导入”时用参考价填明细，员工导出同月单价/金额为空

- 位置：`export_import.php::handle_export_excel()` 第 216–245 行（参考价黄色底纹）vs `handle_export_my_month()` 第 327–330 行（未导入时 G/H 列留空）。
- 影响：管理员与员工拿到的同月明细金额不一致；员工无法提前核对预算。
- 建议：明确“报价前不展示金额”的口径并在两处统一；或员工端同样展示参考价并标注“参考价”。
- 预估：0.2 人日。

## 六、不建议动的部分

1. **维保合同状态由到期日派生**（`MaintenanceService::contractStatus`：90/60/30/过期/无到期日）：不要引入独立“工单状态机”字段。当前模块没有工单/派单/认领实体，审计清单里的“派单、认领、超时”不适用；强行加状态会与预警、报表、导出全部脱节。
2. **采购模块的 MySQL 专用 SQL**（`ON DUPLICATE KEY`、`FIELD()`、`UPDATE ... LIMIT`、`payroll.` 跨库）：生产已合并入主库，为 SQLite 兼容改写会引入行为差异，不建议。
3. **采购角色映射与 `Support` 上下文注入**：管理员/项目账号的 `role`、`project_id` 映射是刻意收口，除 S1 的空项目兜底外不要放宽。
4. **采购没有税率、折扣、出入库单据**：业务形态是“月度采购计划 + 招采报价 + 存档金额”，不是进销存；不建议为审计清单硬加税/库存台账。`stock` 只是员工填的期初库存参考值。
5. **报表用 JSON `row_data` 在 PHP 侧聚合**：与核算存储结构一致，改表成本高、收益低；优先加索引和一次聚合，不动表结构。
6. **维保合同硬删除并级联**：现有编号/唯一约束依赖硬删除，改软删除会牵连导入查重与编号生成，不建议只为“可恢复”改模型。
7. **人员档案导出包含已删除人员**：若业务本意是“历史全量”，只在表头增加“人员状态/是否已删除”列，不要直接过滤。
