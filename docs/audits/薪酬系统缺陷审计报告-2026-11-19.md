# 薪酬系统只读缺陷审计报告

- 审计日期：2026-11-19
- 审计范围：薪酬核算主链路、考勤/绩效录入、工资与绩效导出、权限与数据隔离、事务与重复实现
- 环境：本地 PHP 8.2.33 + PHPUnit 11.5.56，内存 SQLite（`phpunit.xml`），未连接生产库、未写生产数据

## 一、验证方法与结果

### 1. 随机核算 + 独立重算（固定种子 20261119）

- 数据：单项目 24 人，月份 2026-10；随机固定月薪/基本工资、约 30% 人员含月中调薪分段；入职日覆盖年初、月中、次月、缺失；随机离职日。

- 覆盖到的边界：系数空/0/0.5、应出勤存值 0、半天、无入职日、月中入职、月中调薪、离职日、统计列锚定、两套个税模式（普通累计/6 万）。

## 二、严重问题（算错钱 / 丢数据 / 越权）

### S1. 全年发放明细接口漏掉已有的管理人员过滤，项目账号能看到管理人员工资（越权）

**原来加的权限在哪里**
- 2026-09-16 提交 `b162886`（基线：权限收紧）在 `PayrollController::payroll()` 控制器方法内加了数据范围判断：项目账号请求 `type=manager` 直接 403；默认工资表强制 `is_manager_row=false`；项目账号只能看本项目且必须已归档。
- 该权限是“控制器方法内判断 + 查询条件过滤”，不是路由中间件；所有接口统一先走 `requireAccount()`，再用 `isProjectScope()` 判断角色 `scope=project`。
- 这套权限覆盖的是 `/api/payroll`（月度工资表、管理人员表入口）以及导出侧的归档门槛；前端菜单只是入口控制，不构成数据隔离。
- 2026-10-27 提交 `f6ce4ed` 新增「全年发放明细」模块（`/api/payroll/annual`、`/api/payroll/annual/export`），没有复用上面这套分类过滤。

**年度接口的实际路径**
- `routes/api.php` 第 115–116 行直接挂控制器，没有路由中间件。
- `PayrollYearController::data()` / `export()` → `requireAccount()` → `buildView()`；查询条件只有 `year_month` 和 `project_name`（项目账号的项目名），**没有** `is_manager_row / is_case_row / is_hq_row` 条件，也**没有**归档门槛。
- `projectFilter()` 只把项目账号的 `project_name` 固定住，不区分人员分类。

**实测（本地内存库，只读调用）**
- 账号：`scope=project`、`project_name=甲项目`；本地 fixture 的 `project_id=1`（接口本身不返回 project_id，只按 project_name 过滤）。
- `GET /api/payroll/annual?year=2026` → 200，返回：
  - 员工甲 1000（`is_manager_row=0`）
  - 案场甲 800（`is_case_row=1`）
  - 经理甲 5000（`is_manager_row=1`）
- 同一账号 `GET /api/payroll?ym=2026-10` → 200，仅返回 员工甲 1000；经理甲被列表接口过滤。
- 结论：**年度接口放行、月度列表接口拦截**，不是前端隐藏。

**管理人员归属**
- 管理人员是项目花名册里的员工（`person_type=manager`，`project_name` 为所在项目），不是总部/全局人员；核算时单独写入 `is_manager_row=1` 的管理人员工资表。总部人员是另一类 `is_hq_row=1`。
- 因此项目账号看到经理甲属于越权，不是“设计如此”；既有规则明确“项目工资表一律不含管理人员行”。

**为什么“已经加了权限”仍能看到**
- 不是权限完全没加，也不是前端按钮问题；是 2026-10-27 新增年度模块时只复制了 `project_name` 范围，漏了 `is_manager_row` 分类过滤和归档门槛。属于**新接口漏挂已有规则**。
- 影响：项目账号可查看本项目管理人员逐月应发；且核定前也能查看。
- 建议修复：项目范围下在 `buildView()` 增加 `is_manager_row=false AND is_hq_row=false`（案场行按现行“项目可见本项目案场”保留），并补归档门槛；年度导出复用同一过滤。补一条“项目账号年度接口不返回管理人员”的回归测试。
- 预估工作量：0.5 人日（含回归测试）。

### S2. 项目账号的汇总接口把管理人员应发计入项目应发，金额明显偏高

- 位置：`app/Http/Controllers/Api/PayrollController.php`：`summary()` 第 475–517 行；查询只按 `ym + project_name`（482–485 行），未排除管理人员行。
- 触发条件：项目账号打开“汇总展示”，本项目存在管理人员工资行。
- 实测证据：造 甲项目 员工 1000 + 案场 800 + 管理人员 5000，项目账号 `/api/summary` 返回 **6800**；其中 5000 为管理人员应发。案场 800 是否应计入项目汇总需业务确认，但管理人员部分与员工视图/导出汇总的隔离口径矛盾。
- 影响：项目预算执行率、应发合计被放大（示例放大 6.8 倍）；项目账号看到不应可见的管理成本汇总。`/api/summary/export` 同样缺少归档门槛。
- 口径说明：如果业务把“项目汇总”定义为项目总人力成本（含管理），则这部分不算越权，但仍与工资列表/导出的“项目视图不含管理人员”口径不一致，需要统一并在页面标注；如果按员工工资口径，则应排除管理人员行。
- 复现：同上，调用 `/api/summary?ym=2026-10`，比对 `items[].gross` 与员工工资表合计。
- 建议修复：项目范围下汇总只取员工行（`is_manager_row=false AND is_hq_row=false`），案场行是否单列由业务确认；项目范围增加归档门槛；导出汇总同步。
- 预估工作量：0.5 人日（含回归测试）。

## 三、一般问题

### M1. 微调把绩效系数从 0 上调后，绩效工资仍为 0

- 位置：`app/Http/Controllers/Api/PayrollWriteController.php::adjust()` 第 360–394 行；`app/Services/PayrollCalculator.php::computeRow()` 第 946–947 行。
- 原因：核算时 `perf_pay_ref = round(perf_pay * denom / (actual * coef), 2)`，当原 `coef=0` 时该基准被写成 0；微调再按 `perf_pay_ref * perf / req * 新系数` 计算，结果恒为 0。
- 实测：真实核算生成 `coef=null → coef=0、perf_pay=0、perf_pay_ref=0`；通过 `/api/payroll/adjust` 把系数改为 1，`perf_pay` 仍为 **0**（应为 1000）。
- 影响：手工补录系数后绩效不发放，且界面不会报错；只能整月强制重算才能恢复。
- 建议：当 `coef=0` 时用 `max(0, fixed-base)` 作为满勤绩效基准，或微调路径改为按薪资段重新计算，而不是依赖可能为 0 的 `perf_pay_ref`。增加“0→非0”回归用例。
- 预估工作量：0.5 人日。

### M2. 应出勤为 0 时，核算与微调两套算法不一致（主数据来自考勤表）

**应出勤的完整来源**
- 考勤模板列名：`应出勤(天)` 或 `应出勤(手填)`；上传解析时统一映射为 `req_attend`。
- 存储位置：`payroll_attendance.rows` 的 JSON 里，按人存 `{ "req_attend": 数字或 null, ... }`；不是独立数据库字段。
- 留空：解析为 `null`（缺失语义）。核算时 `storedOrFallback()` 对“字段不存在或 null”回退为按考勤符号数出来的应出勤天数。
- 填 0：解析为 `0.00`，按显式 0 处理，不回退。考勤上传的一致性校验明确排除了 `应出勤(手填)` 列（注释写明它与符号统计本来就可能不同），所以填 0 会直接落库、不报错。
- 核算取值：`computeRow()` 里 `h = storedOrFallback($att,'req_attend', $hFallback)`；`hFallback` 默认是按 `in_required` 符号统计的天数（若规则 `prorate_base=calendar` 则为当月日历天数）。
- 微调入口：前端微调弹窗确实有可编辑的“应出勤(天)”输入框，后端 `adjust()` 也允许 `req_att` 字段；所以用户即使主要在考勤表填，微调里仍能改，且会覆盖核算值。

**核算对 0 的兜底**
- 位置：`PayrollCalculator::computeRow()` 的分母逻辑。
- 条件：`h <= 0` 时，若实际出勤 `actual > 0`，分母改用当月日历天数；若实际出勤也为 0，分母用 1。
- 注意：落库/展示的 `req_att` 仍保留 0，只有“除法分母”被兜底；基本工资 = 基本工资基数 × 实际出勤 ÷ 日历天数。

**微调对 0 的处理**
- `PayrollWriteController::adjust()` 在出勤/系数字段变动时重算：
  - `req > 0`：`base_pay = base_pay_ref × act_att ÷ req_att`；
  - `req = 0`：`base_pay = 0`，绩效也为 0，**不**走日历天数兜底。
- 之后的 `recomputeDerived()` 只重算应发/社保/个税/实发，不会回头重算 `base_pay`。
- 实测：基本工资 4000、实际出勤 22、2026-10（31 天），核算路径为 **2838.71**；把应出勤微调成 0 后为 **0**。

**结论：应该修在哪一端**
- 主数据在考勤表，**不建议把核算兜底直接改成“应出勤 0 就发 0”**：如果有人确实整月无应出勤、但临时出了几天勤，改成 0 会少发；反过来，兜底成日历天数也可能在“0 应出勤代表不应发工资”的场景多算。
- 优先修**微调端**：让微调复用核算的同一分母规则（`req=0 && act>0` 用日历天数），或者干脆把微调里的“应出勤”设为只读（以考勤表为准），避免两条路径各算一套。
- 其次在**考勤上传**加提示：显式填 0 且实际出勤 > 0 时给 warning（允许确认后继续），而不是静默落库。
- 核算兜底保留，但触发时记录日志/提示，避免“悄悄按日历天数发钱”。
- 副作用：微调改成日历兜底，会让“0 应出勤但实际出勤 > 0”的人按天拿钱；设为只读则管理员无法在微调里纠正错误应出勤，只能重传考勤。需要业务确认 0 的语义后再定。
- 预估工作量：微调对齐 0.3 人日；上传 warning + 核算日志 0.3 人日。

### M3. 带公式版存在常量回退，且校验区只比合计，无法发现逐行公式不可复算

- 位置：`app/Http/Controllers/Api/ExportController.php`：`basePayFormula()` 1274–1286、`perfPayFormula()` 1289–1324、`sickPayFormula()` 1327–1347；校验区 `fillCheckArea()` 1571–1621。
- 现象：分段薪资、季度绩效、试用段、病假基数不匹配等场景，三列会退化为 `=ROUND(常量,2)`。随机 16 行样本中 88 个非零公式单元格有 3 个为常量（1 行月中调薪的应发基本/绩效/病假）。
- 校验区只比较“系统合计 vs 公式合计”，逐行“+1/-1”可相互抵消而显示一致；同时未覆盖自定义 `formula.gross / formula.net` 的情况——导出公式固定按默认口径生成，系统设置改公式后校验区会整体报差异。
- 影响：文件打开后改出勤/系数不会重算这些行；“校验通过”不能证明公式可复现算法。
- 建议：能拆中间列的场景拆列（如分段明细/绩效出勤列）；不能拆的保留快照但明确标注；校验区增加逐行差异列或逐行校验；对自定义公式明确提示“导出公式仅按默认口径”。若接受现状，应在说明页写明常量回退规则。
- 预估工作量：1–2 人日（取决于是否拆中间列）。

### M4. 微调“更新工资行”和“写审计日志”不在同一事务

- 位置：`PayrollWriteController::adjust()` 第 419–440 行。
- 影响：日志插入失败时工资行已更新，响应 500，但无审计痕迹；重复提交可能产生多条日志。
- 建议：将 update + insert 包进 `DB::transaction`。
- 预估工作量：0.2 人日。

### M5. 人员分类变更后旧类别工资行可能残留，导致重复计入

- 位置：`PayrollCalculator::calculateGroup()` 第 423–476 行只删除当前 scope 的行；`categoryMap()` 第 89–108 行按月取当前 `person_type`。
- 触发：人员从 staff 改为 manager（或反向）后，只重算管理人员表、未重算员工表；旧员工行仍在。导出/汇总会同时出现员工行与管理行。
- 影响：重复计入应发，汇总金额偏高；年度接口按人去重时可能取到错误类别的行。
- 建议：分类变更生效时按 `staff_legacy_id + year_month` 清理旧类别未归档行，或在四类核算入口统一做“同一人同月只保留当前类别行”的清理；补分类变更回归用例。
- 预估工作量：0.5–1 人日。

### M6. 季度/半年度绩效比例无校验；季度基数存在双重折算疑点（待业务确认）

- 位置：`app/Services/CalcRules.php::getPayRule()` 183–223 行；`PayrollCalculator::monthlyPerfBase()` 1894–1905、`employmentRatio()` 1946–1958、`accumulateQuarterPerf()` 1823–1863。
- 现状：`quarter_ratio`、`half_year_ratio` 直接取配置值，未校验“4×季度比例 + 2×半年度比例 ≤ 1”，配置错误会超发。
- 疑点：季度满勤基数先乘“在职日历天数占比”，季度出勤率又用“实际出勤/应出勤”；年中入职当月可能被折算两次（示例：16 日入职、出勤 10 天、应出勤 22 天，基数×16/31 再×10/22）。
- 影响：可能少发/超发季度绩效；需业务确认口径后再改。
- 建议：保存规则时校验比例；对年中入职季度绩效给出明确口径并加单测。
- 预估工作量：0.5 人日（校验）+ 业务确认后 0.5–1 人日。

### M7. 年度/汇总接口按全年全量加载，项目账号也先全量后分组

- 位置：`PayrollController::summary()` 489–491 行；`PayrollYearController::buildView()` 93–100 行；`ExportController::summaryExport()` 611–613 行。
- 影响：大账套（多年、多项目、数万行）下内存与响应时间偏高；也放大了 S1/S2 的越权面。
- 建议：SQL 层按项目/行类型过滤后再分组；年度查询按 `year_month` 索引分页或按人聚合。
- 预估工作量：0.5 人日。

## 六、结论与建议优先级

- **是否存在影响金额正确性的缺陷**：
  - 自动核算主链路：本次随机 24 人 + 全量 451 项回归未发现“算错钱”；系数空/0/0.5、应出勤 0、半天、入离职、分段薪资、病假/事假/旷工/缺卡、两套个税均通过独立重算。
  - 存在金额风险的是**微调路径**（M1 系数 0 上调不恢复、M2 应出勤 0 与核算不一致）和**项目汇总口径**（S2 把管理人员应发计入项目）。
- **上线风险判断**：若系统存在项目范围账号，S1/S2 必须在下次发薪前修复；否则管理人员薪酬可被项目账号查看，项目预算执行率会被高估。S1/S2 修复前不建议向项目账号开放年度/汇总/导出入口。
- **建议修复顺序**：
  1. P0：S1 年度接口越权、S2 项目汇总混入管理人员；
  2. P1：M1 微调系数 0、M2 微调应出勤 0、M3 导出常量回退与校验盲区；
  3. P2：M4 事务、M5 分类残留、M6 比例校验、M7 全量加载；
  4. P3：轻微项与精简建议，随版本迭代处理。
- 本次为只读审计，**未修改任何业务代码、未部署、未连接生产库**。
